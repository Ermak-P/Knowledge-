# Portable release installation

Python 3.12 x64 is the declared runtime. The kit keeps distribution names knowledge-p0 and harness-p0, version 0.3.0rc1, and existing CLI/import names. Windows release qualification is independent of implementation; consult QUALIFICATION.json. Verify the external ZIP SHA-256 before extracting. No SDK/model/cache or project data is part of the distribution.

From an extracted kit: `python install.py install --env "/new path/Knowledge Env" --profile knowledge`. Use `install.sh` on POSIX or `install.ps1` under Windows PowerShell 5.1. Both propagate failures and quote arguments. The launcher discovers Python; `KNOWLEDGE_PYTHON` selects an explicit executable on both launchers; otherwise the Windows launcher prefers a supported Python on PATH before the py -3.12 fallback. Python must already exist; an incompatible Python/venv is preserved and refused.

Core install is offline: two local pure-Python wheels, `pip --no-index --no-deps`, ensurepip from the declared Python. Knowledge-only installs one wheel, imports no Harness/MCP and needs no model service. Add Harness by repeating with `--profile full` in the same owned environment. This creates an environment ownership marker; existing unmarked venvs require explicit `--adopt`, which grants only product package installation/removal and never venv deletion. Run `python install.py doctor --env PATH`.

Optional MCP uses `--mcp-online` and optional-mcp.lock with pinned transitive versions, normal TLS and package indexes. This is an online optional profile, not a complete offline MCP/Windows wheelhouse. Standalone core has no third-party dependencies. Native .NET 10.0.404 is needed only for .NET application evaluation; runtime discovery uses native `dotnet`, with the checksum-verified repository SDK as a Linux fallback. Existing incompatible SDKs are never replaced.

Use the environment's native Python (`bin/python` or `Scripts/python.exe`) with `-m knowledge.cli`, `-m knowledge.maintain_cli`, `-m harness.run_cli`, `-m harness.companion`. Configure explicit project roots and fixed trusted recipes. Provider credentials use environment bindings; no keys in project JSON. Native execution is a trusted-program boundary, not an OS sandbox for hostile application hooks. Product transfer and a fresh project identity are supported; raw copies of existing root-bound stores are not portable.

Supported predecessor boundary: accepted P2 Harness is POSIX-only and had no supported native Windows executor. Actual full P2 Harness binary/data upgrade and old-code rollback are verified on Linux. Windows additionally executes real prior Knowledge binaries to generate nonempty graph/history/queue/receipt/positive-ownership state, verifies current upgrade/backup/restore and old Knowledge code/data rollback with the same identity, and separately exercises the complete current-native Harness lifecycle. Old POSIX Harness native execution/migration remains a separate NO_GO; its capability refusal is tested without patching old binaries. Existing root-bound stores are never silently relocated or rebound.
