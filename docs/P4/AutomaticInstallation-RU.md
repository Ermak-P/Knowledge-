# Установка Knowledge MCP и подключение проектов

Если `project-identity-mismatch` блокирует существующий SQLite store до создания
job, используйте [явную миграцию с сохранением данных](SQLITE-IDENTITY-MIGRATION.md).
Fresh, повторная регистрация MCP и обычный `.ai` import не исправляют эту ошибку.

Исправление надёжности: [bootstrap, Code Mode, покрытия и восстановления](CORE-RELIABILITY.md).
Отдельная [локальная проверка Windows/IPM](Knowledge-IPM-Integration-Validation.md)
содержит точные шаги обновления, резервного копирования и отката.

Поддерживаются версии OpenCode с совместимым Promise Plugin API. Нужен Python **3.12**. Установщик находит его
через PATH или Windows `py -3.12`. Если его нет, установите Python 3.12 с
python.org и повторите команду. Автоматическая загрузка Python не реализована.
SDK, Visual Studio, Kafka, модели и серверы inference не устанавливаются.

Из произвольно названного каталога исходников в Windows PowerShell 5.1:

```powershell
.\install.ps1 -McpDir 'C:\LLM\mcp\knowledge'
```

Повторите ту же команду из новой версии исходников для обновления. Ручная сборка,
путь к проекту, профиль и настройки модели при установке не нужны. Можно вызвать
скрипт абсолютным путём из другого каталога: источником служит каталог скрипта.
Исходники можно удалить после установки. Python 3.12, на котором основан runtime,
нужно сохранить. Для готового проверяемого kit используется такая же команда
`install.ps1 -McpDir ...`; прежний `install.py install --env ...` остаётся
низкоуровневым совместимым интерфейсом.

Linux с Python 3.12:

```sh
sh /path/to/Knowledge-Source/install.sh --mcp-dir '/path/to/Knowledge runtime'
```

Новая установка по умолчанию работает в режиме `readonly`. Для сканирования,
подготовки планов и других операций сопровождения укажите `-Mode maintainer`
в PowerShell или `--mode maintainer` в Linux. Обновление сохраняет выбранный режим.
Порядок переноса проектных блокировок и инструкции по обслуживанию SQLite
приведены в [руководстве](KNOWLEDGE-OPERATIONS.md).

Для Linux проверяется переносимый профиль; native Windows PowerShell 5.1 —
отдельный профиль проверки. Поддержку других native-хостов это не доказывает.

Установка MCP по умолчанию использует сеть и полный pinned
`optional-mcp.lock`. Если в проверяемом kit есть полный каталог `wheelhouse`,
используется только он (`--no-index`). Неполный wheelhouse — ошибка, без
автоматического перехода в сеть. Прежняя установка **core** без MCP работает
офлайн; это другой режим, он не заменяет установку MCP.

## Что устанавливается на машине

В `McpDir` находятся `bootstrap`, поколения `runtimes`, стабильный `launch.py`,
`knowledge-init-auto.py`, `README.md`, инструкции в `runtimes/<id>/docs`,
`state`, журналы и marker владения. В режиме `maintainer` используется
`config/provider.json`. Настройки и общая память `shared` сохраняются при обновлении.
Уже запущенный MCP продолжает работать в старом поколении. Перезапустите
OpenCode, чтобы запустить новое поколение. Установщик не завершает чужие процессы
и не утверждает, что уже работающий хост переключился автоматически.

Глобальный каталог хоста — `$XDG_CONFIG_HOME/opencode`, либо
`~/.config/opencode`. Пять шаблонов устанавливаются в `knowledge-machine-templates`, plugin — в
`plugins/knowledge-machine.js`, собственные настройки — в `.knowledge-machine.json`.
Plugin регистрирует исполняемые команды через native registry; шаблоны хранятся отдельно от файловых команд, чтобы конфигурация не подменяла executable callback. Plugin использует нативные `ctx.mcp.transform` и `ctx.command.transform` OpenCode 2.4.0 и добавляет MCP
`knowledge_machine` **в память хоста**, не переписывая пользовательский JSON/JSONC.
Остальные команды, MCP, комментарии и настройки сохраняются. Совпадение имён с
чужими глобальными файлами или конфигурацией — явный конфликт, а не успешный no-op.
Project-local команда с тем же именем тоже блокируется, чтобы не перехватить её.

Проверяются целостность kit, содержимое установленного поколения и реальный
stdio handshake/list-tools без проекта и без модели. Результат содержит
`INSTALLED`, `UPDATED` или проверенный `UNCHANGED`, source identity и путь к логу.
Проверка MCP не означает проверку доступности модели или качества её ответов.

Обновление сначала устанавливает и проверяет новое поколение, затем переключает
собственные файлы и указатель через журнал отката. При сбое прежнее поколение
сохраняется. Повторная команда сначала восстанавливает незавершённую транзакцию.
Хеши файлов сверяются с решением об обновлении ещё до создания журнала.
Если собственные файлы параллельно отредактированы, автоматическое восстановление
останавливается и сохраняет эти изменения для разбора. Не удаляйте marker/journal
и не подменяйте их: это не способ обойти конфликт владения.

Старый venv принимается автоматически только при проверяемом
`knowledge-release-install.json`, совпадении корня, допустимых пакетах и целых
RECORD. Он сохраняется на месте. Чужой каталог/venv не присваивается; проекты
при машинном обновлении не перечисляются и их базы не обновляются.

### Windows: временный путь и повтор после сбоя

Настраивать `TEMP`/`TMP` вручную не требуется. Системный TEMP может содержать
короткое имя 8.3 с `~`: установщик разворачивает имя собственного временного
каталога через `GetLongPathNameW`, проверяет совпадение файловой идентичности
и повторяет проверки symlink/junction для обоих написаний. Запреты в
`safe_path` сохраняются, включая запрет непроверенных имён с `~`.

В полном логе `<McpDir>/logs/<id>.log` записываются исходный и полный временный
путь, фактический путь проверяемого provider-файла и причина отказа. При отказе
проверки provider его путь, причина и расположение лога также выводятся в
терминал. Содержимое конфигурации и значения ключей не выводятся.

Если первая установка остановилась до активации, marker остаётся `preparing`, новый
runtime не объявляется установленным. Обновите исходники/kit и повторите ту же
команду `install.ps1 -McpDir 'C:\LLM\mcp\knowledge'`. Удалять `McpDir` или вручную
исправлять `site-packages` не нужно; существующее активное поколение сохраняется.

## Один провайдер для всех проектов

Единственный общий файл — `<McpDir>/config/provider.json`:

```json
{
  "provider": {
    "endpoint": "http://127.0.0.1:9000/v1/chat/completions",
    "model": "controlled-demo",
    "evidence": "test-double"
  }
}
```

Это демонстрационные настройки. Установщик не запускает сервис на 9000 и не
ищет реальную модель владельца. Измените общий файл на фактические настройки
своего OpenAI-compatible провайдера. `evidence: live` задаётся явно только для
реального провайдера. Для ключа используйте `key_env: ИМЯ_ПЕРЕМЕННОЙ`, без значения
ключа в JSON. Допустимые поля: `endpoint`, `model`, `evidence`, `key_env`.
При удалённой передаче ключа нужен HTTPS.

Явная project-конфигурация содержит абсолютный `provider_ref`; inline provider
и ссылка одновременно запрещены. Старые inline runner читаются как раньше.
Только явный `/knowledge-init` переводит конкретный runner на общую ссылку,
сохраняя recipes, limits, capture и memory. Не устанавливается выдуманная сборка.
Используйте обновлённый Harness из того же продукта для runner с `provider_ref`;
старый Harness без поддержки ссылки требуется обновить обычным способом.
Переход не продлевает enrollment/approval: штатная проверка drift потребует
нового review там, где он нужен.

Каждая следующая операция разрешает общий файл заново. Эффективная конфигурация
и ссылка входят в authority/hash Harness и fingerprint машинного плана.
Изменение провайдера не разрешает старому плану выполнить новые эффекты.
При обновлении user-edited provider сохраняется. Factory default обновляется,
только если его SHA-256 всё ещё совпадает с предыдущим записанным default.

## В проекте

Откройте свой проект в перезапущенном OpenCode и выполните:

```text
/knowledge-init
```

Корень определяется из активного workspace и Git top-level, включая worktree.
Несколько roots требуют разрешить неоднозначность; случайный выбор запрещён.
Новая `.knowledge` создаётся и сканируется. Существующие P0/legacy `.ai`
используют только штатные preview и отдельные точные approval; скрытой миграции
нет. Установка машины не создаёт `.knowledge` в исходниках или текущем каталоге.

Сканирование работает отдельным durable worker. Checkpoint и диагностика лежат
в `<McpDir>/state/projects/<root-identity>/full`, вне дерева проекта. Агент
автоматически наблюдает статус до завершения; вручную переносить scan ID или
вызывать каждый chunk не нужно. ID доступен сразу после первого успешного chunk.
Лимит файлов ограничивает извлечение, а не время полной инвентаризации/хеширования.
Хост может завершить запрос, worker продолжит работу.

При CLI/JSON/coverage/stale/timeout/no-progress ошибке работа останавливается.
После наблюдения результата `{"resume":true}` явно повторяет временно заблокированные
чтения того же snapshot и scan ID. Уже обработанные файлы не извлекаются заново.
Ошибки исходного snapshot этим не обходятся; изменившийся snapshot требует
явного `{"fresh":true}`. Если неизвестен исход первого chunk и нет checkpoint,
сначала нужен `knowledge.cli scan-status`, автоматический новый scan запрещён.
Сначала изучите `last-result.json`, `last-error.json`, `progress.log` и штатный
`scan-status`. Timeout не доказывает отсутствие commit. После наблюдения исхода
явно используйте JSON `{"resume":true}`; если исправление изменило снимок или
предыдущий scan необратимо заблокирован — `{"resume":true,"fresh":true}`.
`fresh` выбирает текущий снимок, не стирая историю. Бесконечных retry нет.

Успешная инвентаризация даёт `coverage_complete: true`, но семантика остаётся
`PARTIAL`: лексическое извлечение .NET и учёт файлов не доказывают понимание
бизнес-логики, runtime, конфликтов и удаления компонента. Сомнительные,
зависимые/изменённые утверждения включаются в reconciliation/diagnostics.
Инициализация и обновление только предлагают кандидатов, без apply/ack.

После работы над проектом:

```text
/knowledge-candidates-update
```

По умолчанию анализируются изменённые/новые файлы относительно HEAD. Для диапазона:

```text
/knowledge-candidates-update {"base":"<commit>","head":"HEAD"}
```

Извлекаются только файлы incremental scope, хотя inventory/hash остаётся полным.
Для проверки ID используются прежние наблюдения неизменённых файлов с теми же
хешами и partition. При нехватке такого кэша автоматические предложения
удерживаются с явным пробелом анализа: нужен явный полный `/knowledge-init`
или проверенный v2-кандидат; скрытого полного извлечения нет.
Удалённые файлы и недостаток семантического инструмента требуют review; этот
режим не выдаёт лексическое отсутствие за доказательство retirement. Для
проверенных add/update/retire/supersede предусмотрена подача source-bound v2
кандидатов через тот же backend/Store.submit. Их CAS/доказательства/граф проверяет
штатный plan; неподдержанные выводы не имитируются. Dispositions сохраняются.

```text
/knowledge-candidates-push
```

Команда показывает операции, блокеры и **точный fingerprint**, ничего не применяя.
Отдельно подтвердите увиденный fingerprint:

```text
/knowledge-candidates-push {"approve":"sha256:<показанный fingerprint>"}
```

Backend повторно проверит корень, общий provider, source, queue/plan, выполнит
apply, acknowledge и validate. Drift требует нового плана и нового review;
старое approval не подставляется в новый. При неизвестном исходе после commit
наблюдайте состояние, затем используйте acknowledgement-only recovery
`{"action":"recover","plan":"sha256:<одобренный fingerprint>"}`. Он не применяет
PREPARED план и не ремонтирует SQLite напрямую. История остаётся доступной.

## Диагностика без хоста

Собственный глобальный `.knowledge-machine.json` содержит абсолютные `python` и
`launcher`. Через них можно вызвать backend с JSON stdin:

```powershell
'{"action":"status"}' | & '<McpDir>\bootstrap\Scripts\python.exe' -I -X utf8 '<McpDir>\launch.py' command knowledge-init --root 'C:\Projects\My Project'
& '<McpDir>\bootstrap\Scripts\python.exe' -I -X utf8 '<McpDir>\launch.py' mcp --self-test
```

`knowledge-init-auto.py` — совместимый launcher того же `knowledge.auto_init`;
низкоуровневый `python -I -m knowledge.cli knowledge-init` выполняет **один** chunk.
Цепочка slash → worker → helper → chunk конечна; низкоуровневый CLI не вызывает
helper обратно. Для прямого использования helper задайте `--root`, а диагностику
держите вне проекта. Входящий текст исходников никогда не является approval.


## Confluence и объединённое применение кандидатов

После обновления и перезапуска OpenCode 2.4.0 доступны также
`/knowledge-confluence` и `/knowledge-update`. Первая команда запоминает несколько
обязательных разделов, необязательные space keys и разрешение автономного поиска.
Она использует уже подключённый Confluence MCP; Knowledge не запрашивает токены
и не устанавливает отдельный REST-клиент. Существующий проект не требует
повторного `/knowledge-init`. Настройки Harness runner эта команда не переводит.

`/knowledge-confluence` выполняет сохраняемый обход с пагинацией, проверку native
versions и анализ новых/изменённых страниц. Неизменившиеся версии пропускаются;
текст с тем же хешем под новой версией не анализируется повторно. Прогресс и
незавершённые задания сохраняются. Законченные кандидаты остаются в очереди:
`/knowledge-update` готовит объединённый план Git/Confluence, который применяется
только отдельным вызовом с одобрением точного fingerprint. Старое имя
`/knowledge-candidates-push` сохраняется.

Подробности, ограничения доступа и проверка существующего UMUH store:
[Confluence](CONFLUENCE.md), [команда и проверка UMUH](CONFLUENCE-COMMAND-RU.md).
