# Consistent backup, approved restore and rollback

Commands: `knowledge-maintain backup-preview --root ROOT --destination ABSENT.zip`; save/approve the exact preview using `apply`. Restore: `restore-preview --root ROOT --archive BACKUP.zip --recovery ABSENT_DIRECTORY`, then exact approved `apply`. API equivalents are knowledge.maintenance.preview/apply/status/recover.

Lock/freeze order is execution file lease -> exclusive maintenance gate -> SQLite snapshots. This freezes participating Knowledge/Harness writers/readers and refuses active/unverifiable owned processes. Consistency covers both SQLite stores, all their tables (including positive observation metadata, revisions, receipts, requests/actions/outbox), configuration and referenced artifacts. SQLite is copied by its backup API, never by ignoring live hot journals. Application files are not copied/overwritten. External arbitrary host writes/build hooks are outside this coordination boundary.

The ZIP manifest binds root identity, OS, product/schema versions, source identity, per-file SHA-256 and semantic table counts. Every member is validated before restore: bounded size/count, exact allowlist/inventory, no traversal, duplicate/case-colliding names, links, tampering or mismatched project/platform. Provider credentials are outside stores in environment bindings. Backups retain application knowledge/log data and should be protected as project data; they are never included in product distributions.

Restore stages verified metadata, preserves replaced metadata in the explicitly chosen recovery directory, fences ordinary access, then replaces individual metadata directories. It is not one filesystem transaction across directories; journal/fence recovery reconciles each rename and validates identities. Interrupted restore cannot become ordinary success. Locked-file/access errors are failures; recovery retains the fence and old state. Unrelated user source bytes are preserved. Pending/committed histories are not silently acknowledged.

Rollback code and data together: use the compatible new tool to restore the pre-upgrade archive first, then install the retained prior wheels offline in the same isolated environment. Verify actual package versions, Store.validate, histories/queues and safe run inspection. The release verification exercises accepted P2 wheels against real nonempty restored state. Downgrading code alone does not prove data compatibility. Never remove hot journals or delete stores to force rollback.

Relocation policy: package transfer and onboarding an independent new project are supported. Existing store/run relocation/rebind is deliberately unsupported. A different root or OS restore is refused. Preserve the original complete backup/history; initialize a new root explicitly and rediscover/review evidence. Do not rewrite project hashes, approvals, absolute artifact paths or native process identities. This is not cross-machine active-run migration.

SQLite BEGIN IMMEDIATE reservations also refuse active prior-version writers that do not know the new gate. Reservations remain held for backup/compatible upgrade. Restore validates the entire staged set, persists its fence, then closes its own DB handles before native directory replacement. Current participating clients remain fenced; legacy/unaware tools must be stopped during restore, as with any offline metadata replacement. No arbitrary host process/file write exclusion is advertised.

The execution freeze holds a stable root .harness-writer.lock and the legacy metadata lease. Only after the durable restore fence and full staging validation does it close handles inside metadata; stable root ownership and the exclusive gate continue through replacement/recovery. This permits NTFS directory replacement without releasing current executor ownership.

Supported predecessor boundary: accepted P2 Harness is POSIX-only and had no supported native Windows executor/profile. Actual accepted P2 binary upgrade and old-code/data rollback are verified on Linux. Native Windows verifies the complete current-code nonempty lifecycle, metadata rollback/reinstall and a real old-binary capability probe; the old Windows root is preserved and its identity rebind is refused. Fresh standalone Windows qualification does not qualify P2 native migration; that separate profile remains NO_GO. Preserve the original root/backups and onboard a fresh Windows identity instead of copying or rewriting old state.
