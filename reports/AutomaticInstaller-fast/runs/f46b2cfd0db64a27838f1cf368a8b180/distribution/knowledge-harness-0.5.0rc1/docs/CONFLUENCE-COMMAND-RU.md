# Confluence в OpenCode 2.4.0 и проверка существующего UMUH store

Обновите установленный Knowledge обычной командой из новых исходников или kit:

```powershell
.\install.ps1 -McpDir 'C:\LLM\mcp\knowledge'
```

Перезапустите OpenCode 2.4.0. Проверьте наличие `/knowledge-confluence` и
`/knowledge-update`, а также прежних трёх команд. Уже подключённый Confluence MCP
должен предоставлять реальные page IDs, native versions и содержание страниц.
Инструменты детей, пагинации, metadata-only и поиска команда обнаруживает по
фактическому каталогу. Отсутствие возможности явно отражается как пробел покрытия;
REST fallback и хранение токенов не используются.

Первый `/knowledge-confluence` задаёт три вопроса одним запросом: несколько
корневых URL/разделов, необязательные space keys и разрешение автономного поиска.
Можно разрешить только автономный поиск. Область сохраняется локально в Knowledge;
следующие вызовы её используют. Изменить её можно явным запросом пользователем
или аргументом команды с новым полным `scope`:

```text
/knowledge-confluence {"scope":{"roots":["https://docs.example.invalid/wiki/pages/101","https://docs.example.invalid/wiki/pages/200"],"spaces":[],"autonomous":false}}
```

Замените синтетические URL собственными. Обязательные разделы и все доступные
дочерние страницы обрабатываются раньше автономного поиска. Прогресс показывает
фактически сохранённые страницы и задания. По умолчанию бюджет — 100 операций;
`/knowledge-confluence {"extra_operations":100}` продолжает незавершённый обход.
Это ограничивает работу, а не объявляет покрытие полным. Прерванные задания,
незавершённая пагинация и анализ сохраняются. Не нужно удалять `.knowledge`.

Проверка в существующем UMUH/IPM (приватный проект в этой среде не проверялся):

1. Откройте точный исходный корень проекта. Перед обновлением сделайте проверенный
   backup существующим механизмом `knowledge-maintain backup-preview` и отдельным
   одобрением его preview. Сохраните исходные export, counts, pending queue и
   fingerprints. Не копируйте работающий SQLite/WAL вручную и не сбрасывайте store.
2. Обновите runtime и проверьте `knowledge-maintain doctor --root <UMUH>` и обычный
   Knowledge context. Если обнаружен identity mismatch, используйте отдельную
   документированную identity migration; новый init его не исправляет.
3. Вызовите `/knowledge-confluence` с небольшой разрешённой областью. Store
   сохраняется, повторный `/knowledge-init` не требуется. Команда не редактирует
   приложение, не переводит Harness runner на другой provider и не применяет
   canonical candidates. Проверьте coverage, analyzed и applied отдельно.
4. Выполните `/knowledge-update`, изучите изменения, доказательства, конфликты и
   исходные revisions. Одобрите только показанный точный fingerprint отдельным
   вызовом `/knowledge-update {"approve":"sha256:<точный fingerprint>"}`.
5. Повторите `/knowledge-confluence`: неизменившиеся native versions не должны
   вызывать анализ. Измените одну тестовую страницу — анализируется только она.
   Новая версия с тем же нормализованным текстом обновляет метаданные без модели.
   Изменение title/URL с тем же page ID сохраняет источник и claim identity.
6. Проверьте совместный факт Git/Confluence, второй независимый документ и удаление
   одного подтверждённого источника. Другие доказательства должны сохраниться.
   Timeout/access denied/404/пропуск в поиске не означает удаление. Документация
   о реализации сама по себе остаётся INFERRED, требования и предложения имеют
   отдельную область смысла. Неразрешённые противоречия требуют уточнения.
7. Повторите прежние Git-команды и `/update-by-CR` на контрольном изменении,
   проверьте context, history, pending queue и integrity. При прерывании возобновите
   сохранённый run/checkpoint; не повторяйте одобрение изменившегося плана.

Для локальных CLI-проверок используйте Python выбранного установленного поколения
`<McpDir>/<current.json:runtime>/Scripts/python.exe` (на Linux `bin/python`),
например `-I -m knowledge.maintain_cli doctor --root <UMUH>` или
`-I -m knowledge.cli --root <UMUH> export`. Процедура backup и exact preview/apply
описана в [установке](INSTALL-RU.md). Эти шаги — руководство проверки, а не
утверждение о выполненной проверке приватного UMUH или реального Confluence.

В этой ветке интеграция проверяется на синтетических MCP-ответах и `example.invalid`.
Метрики traversal отражают результаты, переданные MCP-клиентом. Локальная проверка
hash/checksum/quotes доказывает целостность сохранённых данных; она не подтверждает
независимо подлинность удалённой страницы или качество семантического анализа.
