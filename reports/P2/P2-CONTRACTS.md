# P2 contracts, version 1

Knowledge owns `.knowledge`, source discovery, confidence, candidate identity and canonical transactions. Harness 0.2 owns `.harness/runner.json`, `runs.sqlite3`, writer lease, artifacts and delivery outbox. The independently installed Knowledge package has no Harness/provider dependency. No per-project package code is generated. `knowledge.discovery.candidate_preview` remains read-only. `candidate_observe` additionally persists version-1 positive observation receipts through Knowledge's coordinated writer, reusing P1 extraction/identity. Harness does not insert them directly. Ownership requires the exact verified observation, supporting evidence and an approved candidate/revision; a provenance label is insufficient. Missing historical proof or reviewed meaning yields manual review. The read-only `capture_observation_receipts` API exposes their exact candidate/source/observation identity for audit. These receipts do not claim scan coverage or authorize retirement. Harness calls `Store.context` and `Store.submit`, never Knowledge SQL or implicit prepare/apply.

`harness --root ROOT --task TEXT` retains its read-only P1 behavior and legacy `.harness/config.json` (`response_max_bytes`). Its capability label is now `runner: not-invoked`. Execution requires `harness-run`. Configuration version 1 is separate and has exactly `version,provider,recipes,limits,capture`. `configure --input FILE [--init-knowledge]` validates and atomically replaces it under the project lease. Initialization is explicit. Provider: endpoint ending `/chat/completions`, model, optional `key_env`, evidence `live|test-double`. Credentials are read only from that environment variable, sent only to the configured HTTPS endpoint (loopback HTTP allowed), never persisted. Redirects and URL credentials/query/fragment are refused. Unknown config keys/versions fail. Changing configuration during a run blocks it; restoring its original config permits recovery. Widening a task requires a new run, not silent revalidation of old authority.

Recipes are trusted, user-chosen fixed absolute executable argv arrays, kind `build|test`, result `{format,path}`, `rerun_safe`, and explicit nonsecret `env`. No shell interpolation or model-provided extra argv. Only `{artifacts}` is substituted. Build result format `exit`; test formats `unittest`, `trx`, `json`. TRX requires positive all-passed/executed totals, no skipped tests, fresh start time and an owned fresh output directory. JSON assertion results require the current `HARNESS_ACTION_ID`, positive executed integer and failed integer zero. Recipe hooks remain trusted host programs. Config/executable replacement by a hostile host is outside the Harness security boundary.

Tasks version 1 have exactly `version,goal,kind,writable,recipes,existing_test_edits`; kind is coding or read-only. Coding requires scoped paths and selected build and test recipes. Read-only cannot have write/recipe authority. `existing_test_edits` is an explicit exact-file exception; ordinary runs cannot weaken existing tests. New regression tests in task scope are permitted. Config, hidden metadata, build policy files and canonical project-owned argv inputs (absolute or relative), executable/script/module entries are protected, including neutral verifier names. Links/hardlinks refuse. Exact script/test paths in existing_test_edits explicitly authorize those edits and create an event; project-owned executables remain protected even from that exception. Protection is also refreshed under lease for old run state. A narrow application source identity covers all non-cache, non-binary, non-private source files (including `build/`); hidden files except gitignore/gitattributes/editorconfig, private filename patterns, caches, `bin/obj`, stores and linked directories are excluded. Linked source is recorded and never traversed. Oversized source blocks; it is not silently dropped. This is a conservative project profile, not arbitrary-host attestation.

The provider protocol is OpenAI-compatible non-streaming HTTP JSON. Each body contains bounded messages including system version, run/agent IDs and immutable runtime role, assignment, task scope, selected Knowledge/provenance, progress and artifact IDs; named typed function schemas; max_tokens; parallel_tool_calls=false; stream=false. The server returns one assistant message with typed tool calls or JSON final `{version:1,status:done|failed,summary:string}`. Call IDs are unique per response. Unsupported message fields, malformed JSON, duplicate keys, unpaired Unicode surrogates, unknown final versions and oversized bodies fail explicitly. Tool arguments permit exactly declared fields/types. Provider role text never grants privileges. Reasoning content can be accepted but is not copied into another role's context. Streaming, images, arbitrary MCP execution and external agent executables are unsupported.

Authoritative protocol reference consulted 2026-11-15: [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), `/v1/chat/completions`, tool calling (`--jinja`/appropriate chat template), `reasoning_content` and usage sections. Both ordinary text and structured tools are documented there; cache and reasoning token values are subsets of prompt/completion totals. The actual adapter is exercised over loopback HTTP, not a replaced Python provider function. Live llama-server/model quality and OpenCode interoperability remain NOT_RUN without configured infrastructure.

Tools: `read(path,offset?,limit?)`, `search(query)`, `knowledge(task)`, `patch(files:[{path,before:sha256|null,after}])`, `recipe(name)`, `artifact(action)`, `review(verdict,findings)`, `delegate(role,assignment)`, `status()`, `capability(name)`. Dispatch uses the current frame role; schemas are also runtime checked. Main delegates only the five non-Main roles, sequentially, with bounded counts; child delegation is denied. Optional specialist names return explicit unavailable without expanded permissions. Absolute/parent/private/dot/linked/hardlinked paths are refused before access. Project identity is the accepted Knowledge resolver's canonical explicit root identity; copied journals cannot be used in another directory.

State and result JSON version 1: run id, project, task and initial snapshot, config hash, current source, role frames/history, request attempts, pending tool cursor, gates, execution and capture dimensions. SQLite metadata/run versions and project are checked; corrupt/unknown stores refuse without initialization/reset. Monotonic events and INTENT/FINISHED actions preserve identifiers, roles, request signatures and actual receipts. Transitions: running -> completed/completed-degraded/failed/cancelled/blocked/awaiting-capture. Blocked and awaiting-capture may resume after the reported obstacle is resolved; failed/cancelled are terminal. A completed resume returns the stored historical result; inspect its source receipt rather than interpreting it as a new verification. Provider inflight uncertainty is blocked for manual resolution and is never replayed automatically. No automatic destructive Git rollback, Git commits of application edits, worktrees, or source reset.

Edits persist exact before/after intent before filesystem writes, then use individual fsynced atomic file replacement. Recovery accepts only owned before/after bytes and unchanged unrelated source; exact after is reconciled without rewriting. This is not a multi-file/SQLite/network atomic transaction. Every patch invalidates all gates, including a no-op patch. Actual recipe receipts bind source/config, invocation, process timestamps, return code, bounded logs, counts/results and attempts. Source changes during a process invalidate its gate. Main final success requires the five completed roles, all configured checks passed on the final snapshot/config and a separate Reviewing approve with no findings. Provider success prose has no authority.

Capture runs after execution-passed is durable. Only changed paths and P1-supported source observations can propose candidates; absence/no eligible fact has an explicit reason. Exact payload, capture time, source event and coding action links are stored transactionally in the Harness outbox before `Store.submit`. Delivery acknowledgements store Knowledge's identity/disposition. Exact payload retries deduplicate even after accepted-before-ack death. Semantic prior rejected/deferred proposals remain disposed. Ambiguous legacy observations require manual review. Busy/corrupt/absent stores remain pending; required capture leaves awaiting-capture, optional leaves completed-degraded. Resume retries delivery without edits. Canonical review/prepare/fingerprint approval/apply/ack remains explicit and independent.

Defaults: context 24,000 UTF-8 bytes (entire serialized HTTP body, including tools); response 64,000 bytes; tool result 6,000; process log 20,000; source/patch file 1 MiB; max_tokens 2,048; requests 64; turns/role 16; delegations 16; elapsed 600s; provider deadline 15s; recipe deadline 60s. `limits` overrides positive integers; `reported_tokens` is optional. Context history is dropped as complete assistant/tool groups, Knowledge may degrade explicitly, oversized policy/assignment refuses. Results return bounded partial/artifact markers. Logs drain but store only the cap. Output max_tokens is a provider request setting; actual response bytes are locally capped. Reported token caps are checked after calls, include all roles and refuse unknown usage; they cannot prevent a single request's unseen remote bill. Raw input/output/reasoning/cache fields are retained; only input+output is totaled. Unknown usage stays unknown, never estimated as zero. Request reservations survive failure/crash; all attempts are counted. Time uses client monotonic deadlines and persisted wall timestamps; wall includes paused time, summed component timings are labelled. Retries/delegation/repeated failures terminate through cumulative limits.

Execution host: Linux/POSIX flock, process groups and /proc process start identities. The supervisor starts with isolated Python imports (-I), preventing an application package/PYTHONPATH from replacing its implementation. A supervisor inherits the lease before launching the recipe; cancellation/timeout kills group descendants and verifies cleanup before release. Worker death does not release the supervisor lease. All resume paths load mutable run and configuration after acquiring ownership and recheck terminal state there; a completed run returns without another model call or state save. Resume may stop only recorded processes with matching PID/start/group, then waits a bounded three seconds for ownership; another run cannot take its lease. Same-run resume is a recovery operation and may stop a still-active recipe; use status for observation. Unconfirmed cleanup retains ownership. Programs that deliberately detach/reparent/escape groups, externally replaced executables, hostile concurrent host processes and OS-level resource security need an OS sandbox, not claimed here. Windows is unsupported for execution in this milestone; Knowledge remains portable.

CLI: `harness-run configure|validate-config|run|status|resume|cancel|capture-status|capture-retry|metrics|compare --root ROOT`, plus `--input JSON`, `--run-id ID`, `--mode single|multi`, `--output ABSENT_DIRECTORY` as applicable. Status without run id lists persisted runs, including crashed workers. Configure/run/compare require input; resume/cancel/metrics/capture require an existing run id. Stdout is one JSON object; success 0, operational errors/unsuccessful run 1, argparse usage 2. Stable errors include project-writer-busy, role-tool-denied, path-denied, edit-recovery-conflict, source-conflict, provider-outcome-unknown, configuration-changed-revalidation-required, required-check-missing-failed-or-stale, required-review-missing-blocking-or-stale and *-budget-exhausted. Error detail never includes credential headers. API equivalents are in `harness.runtime`, `harness.engine`, `harness.comparison`.
