# Windows installer: provider path rejection

Ветка: `codex/automatic-installer`. Исходники исправления:
`d8754c40d29a94e8e595cce6e14b6e02fa9d0d64`.

Выполнены статический анализ и сборка комплекта. Тесты и установка исправленного
продукта не запускались. Проверка установки на Windows — **NOT_RUN**. Предыдущие
тестовые прогоны относятся к другим версиям исходников и не подтверждают это исправление.

## Что установлено о причине

По коду до исправления подтверждена следующая цепочка установки **из исходников**:

```text
tempfile.TemporaryDirectory(prefix='knowledge-install-')
  → Path(temporary), без разворачивания коротких имён
  → source_kit: <temporary>/distribution/knowledge-harness-0.5.0rc1
  → installed Python: shared(<kit>/default-provider.json)
  → safe_path → windows_spelling
```

Таким образом, до активации проверяется factory provider во временном комплекте,
а не обязательно `C:\LLM\mcp\knowledge\config\provider.json`. Короткий компонент
TEMP с `~` в этой ветке действительно доходит до запрета `windows_spelling`.
В установке из готового kit проверяется соседний `default-provider.json` из kit;
при обновлении/проверяемом no-op также проверяется существующий общий provider.

**Причина конкретного сбоя владельца остаётся неподтверждённой:** в переданном
traceback нет аргумента `shared`, значения TEMP и полного журнала. Нельзя
утверждать, что именно его путь содержал `USERNA~1`. Теперь фактический аргумент
и причина отказа будут записаны независимо от того, какой из этих маршрутов сработал.

## Изменённые файлы

| Файл | Изменение |
|---|---|
| `installer/knowledge_install.py` | Собственный существующий временный каталог разворачивается `GetLongPathNameW` до сборки/проверки factory provider; проверяется та же файловая идентичность. Все три provider-проверки получают диагностику пути/причины/лога. |
| `packages/knowledge/src/knowledge/project.py` | Прежние ограничения `windows_spelling` сохранены, в `KnowledgeError.details` добавлены отклонённый путь и конкретная причина. |
| `docs/P4/AutomaticInstallation-RU.md` | Повтор установки, короткое имя TEMP и расположение диагностики. |
| Этот каталог отчёта | Статический верификатор, его результат, исходные SHA-256, журнал сборки и обновлённый kit. |

Преобразование не удаляет `~` строковой заменой и не меняет `TEMP`/`TMP`.
Перед API-вызовом запрещены traversal и UNC/device spelling. До и после
преобразования проверяются symlink/junction; `os.path.samestat` связывает полный
путь с исходным каталогом. `safe_path`, запрет тильды, прочие ограничения имён,
проверки reparse points и ownership не отключены.

Лог `<McpDir>/logs/<id>.log` содержит исходный и полный временный путь,
фактический аргумент provider-проверки, её код/причину и stack frames при отказе.
Терминал показывает отклонённый provider-путь, причину и путь к логу. Содержимое
provider JSON, endpoint/model и значения ключей в эту диагностику не включаются.

Проверка provider остаётся до переключения `current.json` и успешного marker.
Первый сбой оставляет owned marker в состоянии `preparing`, которое допускает
повтор установки; состояние `installed` не выставляется. Во время обновления
сохраняется прежнее активное поколение. Новая попытка использует новое поколение;
удалять `McpDir` или менять ownership markers не нужно. Этот вывод основан на
статическом разборе порядка операций, не на выполнении Windows-сценария.

## Поставка и статическая проверка

`scripts/build_p4.py` доставляет исправленный installer как `machine-install.py`,
исправленный `knowledge/project.py` — внутри Knowledge wheel, документацию — в
`docs`. Эти байты сверены с Git-исходниками непосредственно внутри нового ZIP.

Обновлённый комплект:
[knowledge-harness-0.5.0rc1.zip](distribution/knowledge-harness-0.5.0rc1.zip).
SHA-256: `7ff4199229884de3ce31985bf88713c8ea5f078c117e31dd6cdfb40467445163`.
Это сборка со статической проверкой, без заявления о runtime-квалификации.

Воспроизводимая статическая проверка:

```sh
python3.12 -B reports/AutomaticInstaller-Windows-Path-Fix/verify_static.py
```

Она только читает/разбирает исходники, сверяет Git/ZIP/wheel SHA-256 и проверяет
синтаксис, включая код validator subprocess. Installer, Windows API и тесты
не исполняются. Полный результат — `static-check.json`.

## Повтор установки

Получите обновлённую ветку `codex/automatic-installer` и из её каталога выполните
прежнюю команду, либо распакуйте приложенный новый kit и выполните её из kit:

```powershell
.\install.ps1 -McpDir 'C:\LLM\mcp\knowledge'
```

Ручная настройка `TEMP`/`TMP`, удаление `McpDir` и правка `site-packages` не нужны.
Если отказ повторится, новые путь/причина/лог позволят установить его точную причину.
