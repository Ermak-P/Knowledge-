# Opt-in OpenCode v2 companion

The kit targets documented OpenCode v2 project config `mcp.servers` (local server command arrays, optional disabled field), not the historical v1 enabled layout. Authoritative source/provenance is in the review references. Actual OpenCode version/config smoke is separate; if no executable exists, it remains NOT_RUN.

`harness-host preview --root ROOT --task tasks/approved.json` produces a merge preview. Exact approved `apply --input PREVIEW.json --approve FINGERPRINT` preserves current project opencode.json bytes/backups and adds knowledge_local plus harness_companion. JSONC or conflicting/v1 layouts refuse with manual merge guidance; no global config is touched. `doctor` checks root/runtime/config/task identities and optional MCP availability. `remove-preview` plus exact apply restores original bytes, refusing intervening host changes.

Knowledge MCP retains bounded context/current and explicit history. Companion MCP offers doctor/status and execution only by enrolled task name. Its hidden project config binds the task payload digest, so a model cannot replace a source task JSON with broader scope and silently run it. Normal Harness runtime roles/tools/final gates remain authority. There is no arbitrary shell/MCP proxy or native OpenCode subagent permission claim. Optional MCP requires the pinned online extra; offline core remains independent.

Tests launch the real configured stdio server commands from an isolated installation and exercise MCP tools against the active root. Missing optional specialists and real model/host integration are explicit. A project-local wrapper cannot certify the host's own plugins/global policy; inspect active host precedence before adoption. No private MCP service is installed.

P3 review correction: companion previews are version 2. Regenerate an older preview and approve the new fingerprint; version 1 previews and unknown operations refuse. Existing version 1 installation markers remain inspectable and removable through a fresh preview. Each successful installation generates a fresh installation_id, including when reusing the same install preview after removal; an old remove approval cannot remove the newer installation. The product/Knowledge/Harness schema versions are unchanged.

An invocation captures the task payload and exact enrollment, host and runner state once. The runner rechecks this authority after acquiring its real execution lease, then creates and drives the run under that same ownership. It never executes a second task read. Durable companion runs retain the authority snapshot and recheck it under ownership on resume. Changed task/writable/recipe scope, installation, runtime, host or runner state requires review before new effects. Doctor is observational and does not issue reusable execution permission. Participating installation/configuration changes use the same lease; raw external filesystem edits are not an OS sandbox boundary.

Remove approval binds the complete marker bytes and the exact original UTF-8 bytes or original absence. Apply checks current host bytes, runtime/root, runner state and marker under ownership before changing anything. It restores only the approved snapshot, using atomic byte replacement for an original file, and archives the installation marker. Whitespace, Unicode and CRLF are preserved; changed original bytes/absence, enrolled tasks or installation identity invalidate an old approval. Existing host backups and unrelated/global configuration are retained.

Removal claims the actual marker into its history path and checks those renamed bytes before touching host configuration. A changed marker is returned without overwriting a newer active marker; a failed host replacement also returns the marker. Any retained archive after an interrupted or failed external filesystem operation is preservation/recovery state, not a successful removal. Cooperating operations remain serialized by the project lease; no multi-file filesystem transaction or exclusion of arbitrary external writes is claimed.

The required installed-product correction suite is tests/p3_companion_review_driver.py, run by the clean-package rehearsal after optional MCP installation. It executes the same named regressions as the portable suite, including real configured MCP calls with deterministic read/ownership scheduling probes and actual provider/tool/process effect counts. No model or native OpenCode host is implied.
