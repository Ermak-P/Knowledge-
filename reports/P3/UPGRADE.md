# Approved compatible upgrade

For an unpublished replacement candidate, install the supplied release kit even if its version remains 0.3.0rc1. The installer force-reinstalls only its declared local core wheels with --no-index --no-deps, so pip cannot keep an earlier same-version build while updating the ownership marker. Unrelated packages and project state remain retained. Quiesce/restart project MCP/runner processes when updating code; an already running Python process does not reload replaced modules. Verification upgrades an actual original P3 installation, preserves nonempty Knowledge/pending state, imports the new authority implementation in a fresh process and removes its legacy companion marker through preview v2.

Before changing code, quiesce the project and preserve the prior wheel set. In the new compatible installed tool, run `python -m knowledge.maintain_cli upgrade-preview --root ROOT --destination /abs/new-before-upgrade.zip`. Save its `preview` object as UTF-8 JSON and approve exactly its returned `fingerprint` with `apply --input preview.json --approve FINGERPRINT`.

Preview reads existing state; absent/corrupt/unknown state refuses instead of initialization. It describes exact root, source, configuration, all datastore/artifact identities, formats, counts and backup destination. Apply acquires execution ownership, then an exclusive maintenance gate; Knowledge transactions and Harness journal access share that gate. Busy owners/transactions refuse. Root/source/queue/config changes invalidate approval. Backup uses SQLite backup APIs under the same cross-store freeze.

The accepted P2 Knowledge sqlite-v1/P1 extension 1 and Harness run/config 1 need no database rewrite for 0.3.0rc1. Upgrade records a compatibility transaction and full backup, preserving original canonical values/revisions, receipts, queue dispositions, prepared/committed-unacknowledged plans, positive ownership, requests and outbox. It does not acknowledge old transactions or convert stale approvals into new authority. P0's explicit P1 extension upgrade remains a separate existing command; no speculative schema conversion is performed here.

Interruption leaves `.maintenance/active.json`: ordinary access refuses with maintenance-recovery-required. Run `python -m knowledge.maintain_cli status --root ROOT` and `recover --root ROOT`. Recovery finishes the exact journaled compatible operation or reports an intervening-state conflict; it does not reset data or source. After installation, doctor reports actual installed versions. Unknown versions are refused. Historical process receipts remain historical; cross-OS/boot process identities never become kill authority. Unverifiable old pending process ownership requires explicit manual resolution/reinstall of the executor, not a guessed retry.

SQLite BEGIN IMMEDIATE reservations also refuse active prior-version writers that do not know the new gate. Reservations remain held for backup/compatible upgrade. Restore validates the entire staged set, persists its fence, then closes its own DB handles before native directory replacement. Current participating clients remain fenced; legacy/unaware tools must be stopped during restore, as with any offline metadata replacement. No arbitrary host process/file write exclusion is advertised.

Supported predecessor boundary: accepted P2 Harness is POSIX-only and had no supported native Windows executor. Actual full P2 Harness binary/data upgrade and old-code rollback are verified on Linux. Windows additionally executes real prior Knowledge binaries to generate nonempty graph/history/queue/receipt/positive-ownership state, verifies current upgrade/backup/restore and old Knowledge code/data rollback with the same identity, and separately exercises the complete current-native Harness lifecycle. Old POSIX Harness native execution/migration remains a separate NO_GO; its capability refusal is tested without patching old binaries. Existing root-bound stores are never silently relocated or rebound.
